## Third run (run 42495663037, `test-run/series-4`, commit `7930189`, with failure messages)

Regressions: 3. Moved: 2 (user32 win, +157). Fixed: 5.

- `comctl32 toolbar.c:2134` (both arches): "[4] Unexpected number of rows 5
  (expected 9)" - exactly the `bLarger` case; v2 candidate
  `patches/candidates/comctl32-toolbar-setrows-v2/` addresses it (L2 run on
  `test-run/toolbar-v2`).
- `comctl32.x86_64 button.c:2631` x4: "WM_LBUTTONDOWN on radiobutton: the
  msg 0x000f was expected, but got msg 0x0200 instead" - a `WM_MOUSEMOVE`
  arrives where Windows sends `WM_PAINT`. Now seen in **2 of 3 runs**
  (x86_64 only), never on vanilla. Prime suspect:
  `server-mousemove-on-show-hide` (Inventor: the window under the cursor
  gets a mouse move 100 ms after a window is shown or hidden). It is batch 4
  of the test plan; its Windows measurement must cover this sequence (when
  Windows does and does not send that move), and the patch be limited
  accordingly. Not a timing artefact of the test alone.
- `user32 win.c:4866-4882` (run 2 only) did not repeat.

Gate state: two real L2 regressions in the series - toolbar setrows (fix in
review) and the server mouse move (to be measured and limited).
