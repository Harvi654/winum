# Paired comctl32 L2 for the status-bar v2 candidate

2026-11-08. Original, AI-assisted (Codex), LGPL-2.1-or-later.

## Purpose and controlled inputs

Compare the production series with the production series plus the two
`patches/candidates/comctl32-statusbar-v2/` patches. No production patch or
version is changed. The generic vanilla/series comparison would confound this
candidate with the other 62 patches, so this uses a separate workflow.

Both variants use the SHA-256-verified Wine 11.20 mirror archive pinned by
`scripts/build-statusbar-v2.sh`:

- commit `7298a818b79446bae153b8d5aa27235ab3703bf9`;
- archive SHA-256
  `9f516d63e9f814f4dad70ce0a1943211b8a6236008ac3025cf58004091c661db`.

Both test suites use the **same final candidate test source**, including its
ordinary assertions for the corrected behaviour. The baseline uses production
v1 DLLs; its newly added v5 assertions can therefore fail. This avoids comparing
different test line numbers, assertion sets or todo annotations. Original
production tests are retained. Neither runtime is a vanilla Wine build.

## Execution

The **Test status-bar v2 (paired L2)** workflow runs two independent Arch jobs,
one per variant, using the same checkout and dependency recipe. Each builds
Wine with the normal graphics feature profile, WoW64 and tests enabled, then
runs all 29 comctl32 test units in both PE architectures: 58 units per variant.
Xvfb provides one persistent 1280x1024 desktop per variant. Each variant has its
own new prefix; there is no CAD prefix or proprietary component.

For manual reproduction with Wine build dependencies, both MinGW toolchains,
Python 3, Xvfb and xauth installed:

```sh
bash scripts/test-statusbar-v2.sh baseline /path/to/NEW-baseline-results
bash scripts/test-statusbar-v2.sh candidate /path/to/NEW-candidate-results
python3 scripts/statusbar-v2-l2.py compare /path/to/NEW-baseline-results /path/to/NEW-candidate-results
```

Optional variables, exported separately, are `JOBS`, `UNIT_TIMEOUT` (default
900 seconds per unit), and `WINE_SB_L2_WORK` (must be a new directory).
`--prepare-only` before the variant performs source preparation and input
fingerprinting without compiling. Work trees and raw logs stay local to the
runner. CI uploads only bounded `inputs.json`, `results.json` and `l2-report.md`.
It publishes no runtime, source archive or raw test log.

## Acceptance and interpretation

The comparator verifies matching source pins, checkout, production/candidate
patch hashes, and hashes of all test-source files. Both architectures must
enumerate exactly the source inventory. Prefix initialization, missing test
executables, missing units, timeout, missing/duplicate summaries and inconsistent
process exit codes prevent a passing comparison. It flags increased failures
at an assertion location or in total, added skips and reduced check counts.
Shared baseline failures are visible through JSON counts and are not declared
correct. An unchanged all-skipped area is not newly acquired coverage.

This is one run of each variant. A new or timing-sensitive difference requires
inspection and a targeted paired rerun before deciding whether it is a regression;
the harness does not automatically dismiss it as flaky. The known failure of
empty-string `SetWindowTheme` still excludes unthemed-v6 coverage under Wine.
The separate Windows L1 measurements cover that configuration.

Passing this comparison would establish no detected regression in this comctl32
suite configuration. It does not establish Inventor/SOLIDWORKS L4, a week of
normal use, or a fix for Inventor's RT-dependent composition issue. Candidate
promotion remains separate.
